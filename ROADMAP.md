# Roadmap

This is the single living work register for the library: current extraction, follow-up cleanup, type work, component features, rendering fixes, splitting, verification, documentation, and future development. Update it at every material slice. Do not keep a second hidden roadmap in a local plan.

**Reviewed**: 2026-10-23. This revision consolidates the documented direction across the schema UI and its downstream components. It is ready for maintainer review; it does not authorize implementation or select unresolved architecture.

Status keys: `now` (active slice) | `next` (next eligible work, not started) | `later` (deferred) | `blocked` (named prerequisite missing) | `done` (stated package scope delivered) | `dropped` (rejected, superseded, or merged into a named owner).

All statuses describe **this repository**, not whether a similar component exists elsewhere. Copying an implementation is different from proving its runtime behavior. A package build does not prove the demo, interaction fidelity, or release readiness. Historical checks below were recorded for the current support-copy baseline; this documentation pass did not rerun them.

## Scope and ownership

The roadmap covers the whole composition chain: metadata → field descriptors → field display and layouts → forms and tables → navigation, links, resource actions and page hosts. Buttons, lists, overlays, drawers, tasks, errors, styling, accessibility and tests are part of that chain, not incidental dependencies.

Recursive composition is a framework-wide design goal: forms can contain reusable subforms, sections and panels compose field sets and further sections, and menus compose groups and submenus. Each part should retain its contract when embedded. Shared philosophy does not require identical schemas or state implementations across component families.

- **Library work**: reusable components, typed interpretation, composition and packaging.
- **Consumer work**: concrete resource schemas, routes, registrations, permissions, domain widgets, persistence and application integration. The library must support these without owning their policy.
- **Provider dependencies**: query capabilities, relationship loading, dynamic option payloads and live updates. Record their UI-facing contracts here; do not turn this roadmap into a database or backend implementation plan.
- Copy real implementations and required support before separating packages or modernizing behavior. No replacement shells, fake defaults, or invented ports to make the diagram look clean.
- Future sketches remain proposals. Their rows preserve intent and re-entry conditions, not frozen API shapes.

## 1. Current baseline

- `@ember-schema-app/schema` owns the copied resource/display metadata types.
- `@ember-schema-app/ember-schema` owns the real display-info resolver and is the initial home for copied schema-aware UI and support.
- `@ember-schema-app/ember-ui` currently contains `Pill`.
- The UI support closure is copied into `ember-schema`: buttons, collapse/disclosure, popovers, copyable, error/result handling, relative date, generic field display and Section/FieldSet. Package build and typecheck passed for this baseline. Runtime fidelity is unproven; lint, theme and overlay differences remain open.
- `apps/demo` is mid-migration and is not yet a validation gate.

MVP definition: the copied subsystem is assembled in the repository, the package build is restored, the demo can boot with consumer-owned schema data, and this roadmap records every known omission and cleanup. Type-perfect generic propagation is part of the post-MVP hardening work, not a reason to stop the copy.

## 3. Sequencing and review boundaries

1. **Review this consolidation** (`DOC-08`). Resolve omissions and priorities before source migration resumes.
2. **Finish assembly** (`EXT-03`, `EXT-04`, `EXT-12`): forms and layouts, table/config/filter surfaces, menus/interaction support, plus their real dependencies. Preserve explicit omitted paths.
3. **Restore static proof after each copy** (`FIX-09`, `FIX-14`, `VER-02`). The first support-copy build is already green; do not report unfinished root/demo checks as green.
4. **Build the real demo last** (`EXT-09`, `VER-03`) with consumer-owned schema data, subclass registration and real value/state changes. Verify styles, locales, interaction and teardown for the retained subset.
5. **Separate proven package contents** (`EXT-05`, `EXT-06`) without breaking coupled APIs. Extend generic propagation and remove recorded copy debt in bounded slices.
6. **Plan product enhancements separately**: projection policy, widgets, table preferences/selection/live data, richer form adapters and page hosts. Dependencies in each row govern re-entry; `later` is not an implementation commitment.
7. **Distribution and consumer adoption remain separate approval gates** (`EXT-10`, `EXT-11`, `EXT-13`, `REL-01`–`REL-05`).

## 4. Decisions preserved by this consolidation

- Shared field descriptors own resource display. Do not revive a table-only cell registry, legacy `displayField` pipeline or flattened-record rendering contract.
- A future field collection schema can own grouping and placement. It is not the same schema as a form descriptor, data registration or interaction tree.
- Preserve the current root-buffer and flat field-ID-keyed output behavior during copying. Compositional forms/subforms remain an explicit product goal under FORM-19; recursive presentational groups alone do not replace them. Retiring an older nested-state implementation does not reject that capability or decide its future state/output design.
- Conditional option effects replace an ad hoc dynamic-options callback registry. Optional regex conditions remain future work, not part of the current eleven-operator claim.
- Generic form modal/drawer implementations already exist to copy. Old config-specific rendering layers and discriminator migrations are not new library feature work.
- Root-scoped menu interaction and policy-owned keys replace recursive controllers. Open-root Tab entry is a verification/copy concern, not an unimplemented design by default.
- Widget registry, has-many reduction, reactive membership and preset precedence still need design/current-state checks. This document does not select their API shapes.
- Backend storage cleanup, concrete resource actions/widgets and application cutover are not silently transferred into this package's ownership.
